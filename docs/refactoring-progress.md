## 下载调度与文件意图 · 2026-09-07

[服务端下载调度](../server/quic/download.py) 每条流的未确认发送数据最多 131072 字节，
每个连接最多同时调度 8 条下载，因此这些下载流的待确认数据总量最多 1048576 字节。
每次文件读取最多 65536 字节，放在线程中执行；已确认数据释放缓冲后再继续读取。
连接关闭、对端取消和文件错误会停止后续读取；达到任务数上限时返回可重试错误。

Qt 每次异步接收最多处理 65536 字节，处理或写入后通知 MsQuic 继续。
下载元数据未到达时保留一个未完成接收，控制流继续处理消息；
文件流头部限制为 512 字节。上述数字限制的是应用批次和下载发送缓冲，
不代表整个进程、传输库或操作系统的内存上限。

调度模块通过一个集中适配器读取 aioquic 发送缓冲状态。
这部分依赖已固定的 aioquic 1.3.0 内部字段；升级依赖时须运行
[调度兼容性测试](../server/tests/test_download_scheduler.py) 和真实联调，不能仅依赖导入成功。

[文件仓储](../server/storage/repo/file_repo.py) 已校验同一用户文件意图对应的会话、名称、大小、
摘要、方向和下载来源；重试不能替换这些内容。
完成状态保持不变，没有业务变化的初始化、进度和完成重试不再追加同步事件。
下载来源保存到 `file_transfers.source_file_id`，并支持旧数据库添加字段。
旧下载记录缺少来源时保留记录和文件，以冲突错误拒绝猜测来源；用户可明确发起新的下载。

## 原生同步存储与进程重启 · 2026-09-07

本轮继续使用前述 Windows、Python 3.14.3、Qt 6.11.0 和已有构建目录。
[状态存储组件测试](../client/tests/statestore_test.cpp) 验证业务对象、事件标识和连续位置在同一事务中回滚，
重开数据库后重试仍正确；晚到的消息保持撤回/焚毁状态，已读位置不回退，
地址、用户和设备分别保存状态，会话和文件旧版本不能覆盖新状态。

真实联调增加三个场景：强制结束客户端后恢复消息、已读与撤回状态并接收离线消息；
保留一个历史缺口、先收到后续在线消息，再强制结束进程，重启后补齐缺口且不重复推送；
同一 Qt 进程从 Bob 切到 Carol 再切回 Bob，检查消息、会话与恢复位置隔离。
这些场景覆盖已接收状态恢复，待确认写入和文件任务的跨重启恢复仍需实现。

重启测试另复现了服务端接收停滞：向已退出客户端推送后，
Windows 返回 ConnectionResetError 10054，监听仍开放但没有待处理的接收操作，新客户端连接超时。
诊断保存在本机 tmp/native-integration/20260907-100502/；
[监听入口](../server/quic/endpoint.py) 现在在 Windows 下创建并配置 UDP 套接字，

## 上传连接占用与多设备接管 · 2026-09-09

本批针对同一上传意图被两个连接恢复的路径。原文件流只带文件编号，两个连接的字节会被顺序追加到同一文件；
另一设备还可提交失败的 `FileFinish` 改写活动上传状态。
新增两个真实 QUIC 设备场景在修复前均失败，0.816 秒；证据为 `tmp/upload-owner-before.log`。

[上传占用登记](../server/quic/upload.py) 在单服务进程内按用户和文件意图关联当前连接、设备、
连接建立顺序、流编号和已提交位置；占用 = 当前获准写入该上传流的连接及位置。
只有初始化与磁盘协调成功后才授予占用；其他设备在原连接活跃时收到可重试的 429。
同设备后建连接可接管，不同设备等待释放或上传空闲超时；过期比较使用单调计时，
`MINIIM_FILE_STALE_MS` 默认 900000 毫秒，0 禁用超时接管，已认证会话提供设备标识。

[网络入口](../server/quic/server.py) 要求上传流头 `MINIIMFILE2 <file_id> <offset>\n` 与初始化位置一致，
一个占用只绑定一条流，每批写入核对数据库进度与该流位置。旧连接的流、错误偏移和重复流不能追加数据，
旧连接的完成请求不能修改新连接上传；旧连接断开只释放自己仍持有的占用。
流重置、不完整结束、存储失败及取消按相应路径释放占用；完整发送保持占用直到完成确认或后续接管。
拒绝非法 UTF-8、旧格式、负数/错误偏移、超过 512 字节或截断的头部，拆开的合法头部仍可上传。
[Qt 上传组件](../client/core/file/uploadstream.cpp) 写入该格式及起始偏移；下载流格式保持原有语义。
本批不修改 Protobuf 字段或数据库结构，升级须同时重建客户端与更新服务端。

清除等待计时，其他设备的进度仍可正常展示。文件意图、初始化及完成请求均保持原值。

## 跨端成员已读计数与旧缓存纠正 · 2026-09-10

本批完成服务端成员计数修复后的跨端同步。旧客户端根据每个读者的会话位置扣减所有区间消息，
新成员读旧消息会错误减少原收件人的未读人数；页面新增两项回归在旧实现均失败，

[同步协议](../proto/sync.proto) 新增 ReadCountUpdated（SyncEvent 字段号 16），
在已读事务内按实际首次读取的原投递生成事件，发给该消息的原投递用户，包含已离群的发送者；
新成员或离群期间无投递的消息不产生计数变化，重复已读和原请求重放不重复生成计数事件。
[升级代码](../server/storage/repo/read_state.py) 用 `read_count_events_v1` 一次性为既有消息追加计数纠正事件，

[Qt 状态存储](../client/core/sync/statestore.cpp) 将计数按消息单独保存，按事件位置合并；
计数先到、旧计数后到、消息后到与重启均保持最新人数，初始消息提供尚无计数事件时的初始人数。
[页面状态](../web/src/store/session.ts) 消费 `readCounts` 快照和 `readCount` 更新，
Receipt 只推进已读位置及当前用户未读总数。旧缓存缺少计数时标记 `readCountKnown=false`，
页面显示“已读状态同步中”，收到纠正事件后显示人数；计数不能恢复已焚毁或撤回正文。
